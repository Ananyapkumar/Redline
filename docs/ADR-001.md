# ADR-001: Redline — system architecture and initial technology decisions

- **Status:** Accepted
- **Date:** 2026-09-03
- **Author:** Ananya P. Kumar
- **Supersedes:** none

---

## 1. Context

Regulated companies — fintech, healthtech, insurance — must track a continuous stream of
regulatory change and determine which of their own internal policies, controls and
procedures each change affects.

Today this is manual. A compliance analyst reads regulator bulletins and cross-references
them against an internal policy library by hand. Industry sources put horizon scanning and
impact mapping at roughly 30–50% of a compliance analyst's time. The work is slow, it does
not scale with regulatory volume, and a missed obligation is a financial penalty rather
than an inconvenience.

An established commercial category already exists (Ascent, Corlytics, Compliance.ai), which
confirms that organisations pay for this problem to be solved. The opportunity is not in
inventing the category but in the reliability characteristics of the system: compliance
teams cannot use a tool that is confidently wrong, and they cannot audit a tool that cannot
show its reasoning.

### 1.1 Prior work informing this design

The predecessor project (`clause`) established a working pattern for schema-driven
extraction with a measured evaluation harness — 162 field judgements, variance analysis
against a stated noise floor, and a pre-registered accuracy prediction. That pattern is
carried forward. Its limits are what this project is designed to exceed:

| Dimension | `clause` | Redline |
|---|---|---|
| Inputs | 18 synthetic documents | Real published documents, uncorrected |
| Control flow | Single-shot extraction | Multi-step loop with tool calls |
| What is measured | Extraction accuracy | Retrieval, judgement, and citation integrity |
| Invocation | User-triggered | Scheduled, unattended |
| Behaviour when uncertain | Always answers | Abstains and routes to a human |
| Failure handling | Not exercised | Retries, timeouts, idempotency, cost ceiling |
| Volume | 162 judgements | Target ≥1,000 traced runs |

## 2. Problem statement

Given a newly published regulatory document and an organisation's internal policy library,
determine which specific policy clauses are affected, draft the required amendment to each,
and do so with a stated confidence — declining to answer where confidence is insufficient.

**Primary user.** A compliance or GRC analyst at a 200–2,000 person regulated company, who
reviews and approves the system's output rather than trusting it blindly.

**Success for the user.** Their horizon-scanning workload becomes a review queue. They spend
their time judging proposals rather than discovering changes.

## 3. Scope

### In scope
- Ingestion from two public regulatory sources, on a schedule, with duplicate detection
- Conversion of PDF and HTML source documents into structured text with hierarchy preserved
- A clause-level index of an internal policy library (~25 documents, ~400 addressable clauses)
- Extraction of discrete obligations from regulatory text as validated structured objects
- Retrieval of candidate affected clauses, with measured retrieval quality
- Impact classification (affected / not affected / ambiguous) with a verified citation
- Drafted amendment ("redline") per affected clause, with severity and confidence
- Abstention and routing to a human review queue below a confidence threshold
- An evaluation harness over a hand-labelled golden set
- Tracing of every run: cost, latency, retries, tool errors
- A public metrics page reporting quality and reliability

### Explicitly out of scope
- Legal advice. The system proposes amendments; a qualified human approves them.
- Jurisdictional coverage beyond the two chosen sources.
- Multi-tenancy, authentication, or role-based access control.
- Automated application of approved amendments to source documents.
- Fine-tuning of any model.
- Any user interface beyond a functional internal review queue.

## 4. Architecture

```
Regulator sources ──▶ Watcher ──▶ Normaliser ──┐
  (2 feeds, hashed,    (fetch,     (PDF/HTML →  │
   deduplicated)        cache)      structured)  │
                                                 ▼
                                          ┌─────────────────────┐
Policy library ──▶ Clause index ─────────▶│     AGENT LOOP      │
  (~25 docs,       (pgvector,             │ 1 extract obligations│

                                          │ 4 draft, score conf. │

                                    conf ≥ τ ────────┴──────── conf < τ

        Tracing, eval harness and golden set wrap the entire loop.
```

## 5. Decisions

### D1 — Postgres with pgvector, not a dedicated vector database

**Decision.** A single Postgres instance holds documents, clauses, embeddings, run records,
the dead-letter queue and human review decisions. Vector search via `pgvector`; keyword
search via Postgres full-text search.

**Alternatives considered.** ChromaDB (used in `clause`); Pinecone; Weaviate; Qdrant.

**Rationale.** The corpus is ~400 clauses. At this scale a dedicated vector store solves a
problem I do not have, while adding a second system to operate, a second consistency
boundary, and in Pinecone's case a bill. Hybrid retrieval — which regulatory text needs,
because exact phrases such as "twelve months" matter as much as semantic similarity —
requires both keyword and vector search over the same corpus. Postgres provides both
natively; ChromaDB does not. Transactional consistency between a run record and its
retrieved clauses also comes free.

**Consequences.** Scaling past roughly 10⁶ vectors would require revisiting this. That
threshold is approximately four orders of magnitude away and is not a real constraint here.
Reversal cost is low: the retrieval interface is a single function.

### D2 — Hand-written agent loop first, LangGraph port second

**Decision.** The agent control flow is implemented directly as an explicit state machine.
Once it is correct and measured, it is ported to LangGraph as a separate, comparable
implementation.

**Alternatives considered.** LangGraph from the outset (as used in `clause`); CrewAI;
AutoGen; a single large prompt with no loop.

**Rationale.** I have used LangGraph without having written the underlying loop, which means
I can build with it but cannot confidently debug it. Writing roughly eighty lines of
explicit state machine removes that gap. Keeping both implementations makes the framework's
actual contribution measurable rather than assumed.

**Consequences.** Costs approximately one additional day. Produces two implementations to
maintain; the hand-written one is retained as reference and is not required to stay at
feature parity after the port.

### D3 — Structured outputs are schema-validated, never parsed from prose

**Decision.** Every model output that the system acts upon is defined as a Pydantic model
and returned through schema-validated tool calling. Validation failure triggers a bounded
retry; it never falls back to text parsing.

**Alternatives considered.** Requesting JSON in the prompt and parsing the response;
regular-expression extraction from prose.

**Rationale.** Prompt instructions are not guarantees. A parser that succeeds on
malformed input is worse than one that fails, because it propagates corruption silently.
This pattern was validated in `clause` and is carried forward unchanged.

**Consequences.** Constrains model choice to providers supporting structured tool calling.
Occasional retries add measurable cost, which the tracing layer captures.

### D4 — Citations are verified in code, not requested in the prompt

**Decision.** Every clause identifier the model produces is checked against the corpus
before the output is accepted. An identifier that does not exist forces a retry, and
persistent failure routes the item to human review.

**Alternatives considered.** Instructing the model to cite only real clauses; post-hoc
sampling of citations for manual review.

**Rationale.** In a compliance context a fabricated citation is the most damaging possible
failure — worse than no answer, because it looks authoritative and would be acted upon.
This class of error can be eliminated deterministically rather than mitigated
probabilistically, so it should be.

**Consequences.** Hallucinated-citation rate is enforceable at zero and reportable as such.
Requires the clause index to be authoritative and current.

### D5 — The system abstains rather than guessing

**Decision.** A confidence score is derived from retrieval margin, self-consistency across
samples, and validator outcomes. Below a tuned threshold, or on detected ambiguity, the item
is routed to human review with a stated reason rather than answered.

**Alternatives considered.** Always producing a best-effort answer with a confidence
label attached; asking the model to self-rate confidence on a 1–10 scale.

**Rationale.** For this user, a system that hands off 15% of cases and is reliable on the
remaining 85% is usable. A system that answers everything at 85% accuracy is not, because
the analyst must then re-check all of it, which is the work being replaced. Self-rated
confidence is not grounded in anything measurable and is therefore not used.

**Consequences.** Hand-off rate becomes a reported metric and a tunable operating parameter.
Threshold selection requires ambiguous cases in the golden set, which are deliberately
included.

### D6 — Reliability is a first-class requirement, not hardening added later

**Decision.** Retries with exponential backoff on all external calls; a hard per-run
timeout; idempotency keyed on document content hash; a per-run cost ceiling that aborts
runaway loops; failed runs persisted to a dead-letter table with their error.

**Alternatives considered.** Adding error handling once the happy path is complete.

**Rationale.** The system is intended to run unattended on a schedule. Unattended operation
is precisely where unhandled failures become expensive — silently, and overnight.
Retro-fitting idempotency in particular is substantially harder than designing for it.

**Consequences.** Adds roughly one day of build time and a permanent constraint on how
new components are written.

### D7 — Judged outputs require a validated judge

**Decision.** Drafted amendments, which have no single correct string, are scored by a
rubric-based LLM judge. The judge's agreement with hand-grading is measured on a sample and
reported alongside every judged score.

**Alternatives considered.** Reporting judge scores directly; exact-match scoring; omitting
the measurement.

**Rationale.** An unvalidated judge manufactures false confidence, which in an evaluation
harness is worse than having no metric at all. If judge–human agreement is below roughly
80%, the metric is not usable and this will be stated rather than concealed.

**Consequences.** Requires hand-grading approximately 30 outputs. Introduces a metric that
may need to be publicly reported as unreliable.

### D8 — Deployment is a container on a managed platform

**Decision.** Docker image deployed to Fly.io or Railway with managed Postgres, a scheduled
job, and alerting on dead-letter growth and cost-ceiling trips.

**Alternatives considered.** Kubernetes; serverless functions; local-only operation.

**Rationale.** The requirement is a public URL, a scheduled run, and observable failure. A
container on a managed platform satisfies all three. Kubernetes satisfies requirements this
project does not have.

**Consequences.** Platform lock-in at the deployment layer only; the application is a
standard container and portable.

## 6. Non-functional targets

| Property | Target | Verified by |
|---|---|---|
| Retrieval recall@10 | ≥ 0.85 | 40-case hand-labelled golden set |
| Hallucinated citations | 0 | Enforced by validator; asserted in tests |
| Unattended completion rate | ≥ 90% | Batch run without intervention |
| Traced runs before publication | ≥ 1,000 | Historical batch over ~6 months of source data |
| Cost per run | Recorded, ceiling-enforced | Tracing layer |
| Latency p95 | Recorded | Tracing layer |

## 7. Consequences of this architecture

**Positive.** One operational datastore. Every model output is either schema-valid or
rejected. Fabricated citations are structurally impossible. The system's uncertainty is
visible rather than hidden. Every claim about quality is backed by a reproducible
measurement.

**Negative.** The corpus scale ceiling is Postgres-shaped. Two agent implementations exist.
Abstention means the system does not answer every input, which requires a human reviewer to
be available. The eval harness and golden set are hand-built and therefore expensive to
extend.

**Accepted risks.** The internal policy corpus is constructed rather than drawn from a real
organisation, so retrieval difficulty may not fully match production. This is stated openly
in the README rather than obscured; contradictions and stale clauses are deliberately seeded
into the corpus to partially compensate.

## 8. Open questions

1. Which two regulatory sources? Selection criteria: publicly available, permissibly
   accessible without scraping restrictions, meaningful volume over the last six months.
2. Confidence threshold τ — to be determined empirically against the golden set's
   ambiguous cases, not chosen in advance.
3. Whether the LangGraph port earns its place. Decided on measured evidence at Day 50; if
   it does not, the decision and the reasoning are recorded rather than the work discarded
   silently.

## 9. Revision policy

This document is the source of truth for architectural intent. Any decision that changes
gets a new ADR that supersedes the relevant section here. Decisions are not edited in place,
so the reasoning trail survives — including the reasoning that turned out to be wrong.
